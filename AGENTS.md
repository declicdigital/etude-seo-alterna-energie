- Editorial attachment selection and drag-and-drop use the same upload handler in the embedded editorial page, so validation and persistence remain consistent.
- Canonical rubrique and fiche paths use the shared slugs module and a TanStack splat route; editorial-links translates mail paths into internal iframe targets, preserving legacy destinations and sign-in return paths so links stay targeted.
- Article notifications apply recipient-specific field filtering before rendering either HTML or plain text, so both formats respect the same disclosure rules.
- Embedded editorial workflows use the shared browser-safe public pipeline module to normalize split steps and audience/type transitions; archive legacy combined steps, preserve actual dates and publication history, and restore removed steps on reversible type changes.
- Step completion uses the shared pipeline helper and explicitly supplied per-step dates, including separate todo brief/writing dates; never overwrite an entered date; only when a step (or a todo saved with just its doc link) has no date does validation stamp today's date, as requested by the user.
- FAQ requests remain in the request tracker; audience lists derive only from validated records, sorted by validation time, and a database trigger protects validation fields using the authenticated admin role to prevent client-side bypasses.
- The communication kit has its own approved-user route and a static asset manifest; ship original resources and a prebuilt complete ZIP through same-origin Lovable Assets downloads, without changing editorial workflows.
- Invitations use an authenticated admin-only server function and Cloud Auth Invite emails; the public acceptance page sets the initial password, and invitation secrets must never be returned to administrators or copied in email.
- Access activity uses an admin-gated SQL RPC projecting only Auth sign-in time, invitation time and password-presence completion; never return hashes or tokens, and do not infer invitation completion from link clicks or profile approval.
- Brand logos stay scoped to the surface the user points at: the Digicom wordmark replaces the Alterna logo only in the « Demandes d'accès » page header, while every other surface keeps the Alterna logo — never swap a logo site-wide from one screenshot request.
- Review-step recipients are enforced by `notificationRecipients` using the Service Communication list in `src/lib/article-notification.ts`, even when legacy settings specify a partial group; embedded defaults are normalized for visible consistency.
- Manual step reminders bridge the same-origin embedded page to an authenticated server function; verify both Geoffrey’s identity and admin role server-side, and derive content and recipients from persisted article/configuration rather than client payloads.
- The Benchmark tool lives in `public/benchmark.html` with data in `public.benchmark_months` behind `src/routes/api/public/benchmark-months.ts`; reads require an approved session, writes require Geoffrey's admin identity checked server-side via `canEditBenchmark`, and the embedded page sends the session token from same-origin localStorage (no password login).
- The « Organisation » board (`src/components/organisation-board.tsx`) stores columns and cards in `public.org_columns` / `public.org_cards`; RLS and the `org_cards_guard` trigger rely on `can_use_organisation` (admin, or approved with « Organisation » granted in `allowed_sections`, closed by default), authorship is set from the session, and assignee/tag emails go through `/api/public/notify-organisation`, which re-reads the saved card before sending.
- Organisation cards keep links and files in `org_cards.attachments` (jsonb); files live in the private Storage bucket `org-files` under `<card id>/…`, gated by `can_use_organisation` storage policies, opened through short-lived signed URLs, and removed from storage when the attachment or card is deleted.
- Per-step deadlines (`step.deadline`): set automatically by `EditorialPipeline.applyAutoDeadline` (Relecture = Image validation date + 3 business days, Intégration = Relecture validation date + 5 business days, never overwriting an existing deadline) or by Geoffrey in the card (gated client-side by `canRemind`). The next step's deadline is sent as `stepDeadline` and shown in the step mail; the daily `/api/public/jobs/deadline-reminders` job mails the step's assignee on the deadline day (previous Friday for weekend deadlines) via `src/lib/step-deadlines.ts`, once per `reminderStepJ:<space>:<article>:<step>:<deadline>` marker.
- The « D.I.G.I.P.O.T.E » assistant (the user-chosen name of the translucent glass robot; keep it in the UI and system prompt) chat (`src/components/digicom-assistant.tsx`, mounted in `DigicomView`) answers usage questions through `askAssistant` (`src/lib/assistant.functions.ts`, approved users only, Lovable AI gateway with `LOVABLE_API_KEY`). Its knowledge and the only paths it may link to live in `src/lib/assistant-knowledge.ts`, filtered by the person's access server-side; when the AI is unavailable (no credits, 402/429) it answers locally from the same topics. Update the topics whenever a feature changes.
- D.I.G.I.P.O.T.E logs EVERY exchange (question, date, asker's profile name, robot reply, `unanswered` flag) in `public.assistant_questions` (migrations 0010–0011), shown only to Geoffrey (admin + his email, `canSendStepReminder`) on the « Digipote » page (`src/components/digipote-view.tsx`, special sheet `__digipote` → /digipote, sidebar link). Geoffrey's corrections (`correction`) are served to every approved user through the `assistant_corrections()` SECURITY DEFINER RPC and put first in the system prompt. Unanswered detection: the model ends such replies with `[[SANS_REPONSE]]` (stripped server-side by `splitNoAnswer`), and the built-in fallback logs through `logUnansweredQuestion` when no topic matches. Only Geoffrey reads/resolves/corrects them on the Digipote page (the chat header button and the robot badge lead there), whose « Copier les questions à traiter » text (`formatUnansweredForCopy`) is meant to be pasted back so answers get added to `ASSISTANT_TOPICS`. Topics must stay verified against the code — never add an answer that the app does not actually do. The person's real role comes from `TEAM_ROLES` (by login email); the model must not assume roles.
- D.I.G.I.P.O.T.E answers numeric questions from `src/lib/assistant-stats.ts`: on each question the server reads (with the person's own RLS rights, only for rubriques they can open) the editorial articles and « À rédiger » todos of each space, the online lists (workbook base + `sheet_cells` edits via `dataRows`/`getRow`, sub-lists included), FAQ requests and the newsletter calendars, and puts exact pre-computed totals in the prompt. The model must never count by itself; add new figures there when a new kind of question comes up.
- « Bug Buster » mini-game (`src/components/digipote-game.tsx`, opened from the assistant's 🎮 button): 4 maps and 4 robot looks (`ROBOT_SKINS` / `skin` prop of `RobotSvg`; ids shared in `src/lib/game-leaderboard.ts`). Each finished game is saved in `public.game_scores` (migration 0012) through `submitGameScore`; the `game_scores_fill` trigger sets author, profile name and date server-side (never trust a client name). Leaderboards (best score per player for the day / week from Monday / month, Europe/Paris boundaries, per map or all) are computed by `buildBoards` in `getGameLeaderboard` and polled every 8 s by the game.
- Link previews use `public/og-digicom-v3.jpg` (1200×960, the 5:4 ratio of the Teams link-card thumbnail, as asked by the user; Digicom logo + robot + tagline only, never « Alterna Énergie » on it; bump the file name when it changes, previews are cached by URL) declared with an absolute `APP_ORIGIN` URL in `src/routes/__root.tsx`.
- The production address is the custom domain https://digicom.life (`APP_ORIGIN` in `src/lib/app-url.ts`, used by mails, invitations, share image). `www.digicom.life` and both former `.lovable.app` addresses are in `LEGACY_HOSTS` and redirect with their path (301, or 308 for non-GET); Lovable preview hosts are never redirected. The pg_cron jobs (deadline-reminders, monthly-recap) post to digicom.life.
- FAQ requests: besides admins, Matthieu and Marick (`FAQ_VALIDATOR_EMAILS` in `src/lib/faq.ts`, mirrored by the SQL `can_validate_faq` used in `guard_faq_validation`, migration 0013) validate requests and set/update their link (« Enregistrer le lien », « Mettre à jour le lien »). Each request has `channel` (Zendesk / Site Web); only Zendesk requests have a category (`faqNeedsCategory`).
- Bug Buster duo mode: `src/lib/duo-transport.ts` (Supabase Realtime; private channels `bug-buster:lobby` with presence and `bug-buster:room:<id>` broadcast, policies on `realtime.messages` for approved users in migration 0014, automatic fallback to a public channel if the private one is refused). Players who click « Jouer en duo » are paired by `pickDuoPair` (two longest-waiting, oldest hosts). The host runs the simulation (both robots, `DUO_SPAWN_FACTOR` = twice as many bugs) and broadcasts normalized snapshots at 10 Hz; the guest sends its position/fire presses at 10 Hz and only renders. The host saves the duo score (`mode = 'duo'`, `partner_id`, partner name/approval checked by the `game_scores_fill` trigger); `buildBoards` returns separate `solo` / `duo` boards (one entry per pair).
- « Planning intégré » rubrique (sheet `PLANNING INTEGRE` → /planning-integre, embedded `public/planning-integre.html`, ported from the Lovable project « Planning intégré BDP »): one shared JSON state in `public.planning_state` (id 1), plus `planning_history` (50 versions per year, trigger) and `planning_audit_log` (migration 0015, data copied from the old project). The page reuses the Digicom session from same-origin localStorage through supabase-js `accessToken` (never its own auth client), loads `/vendor/supabase-2.118.0.js`, and never saves before the shared state was read. Reading: `can_view_planning` (admin, or approved with « Planning intégré » in `allowed_sections`, closed by default); editing: `can_edit_planning` (admins + `PLANNING_EDITOR_EMAILS` in `src/lib/planning.ts`). Images go to the private `planning-images` bucket; images imported from the old tool still point to its storage (signed links), so the old project must not be deleted. Layout: a top-right switch « 🗓 Mois par mois » (default board, `renderSimple`) / « 📅 Frise » (the original timeline, sub-views « Par campagne » = `timeline` and « Par canal » = `canal`); choices kept per browser in localStorage `planning_view` / `planning_frise_view`, theme in `planning_theme`. Every URL typed anywhere in the planning is turned into a short clickable chip (`a.pl-link`, MutationObserver at the end of the page script; clicks on it never open the card behind).
